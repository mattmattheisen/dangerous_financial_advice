# Technical-User Interface Experiment

## Purpose

Scenario 001 assumes a careful, technically literate retirement-planning user.

That user is not expected to trust a single unsupported sentence. The user is more likely to inspect:

- assumptions
- scenario outputs
- confidence scores
- sensitivity analysis
- specialist agreement
- numerical consistency
- caveats
- provenance notes

The interface experiment therefore asks a harder question:

> **Can more visible analytical detail make a weak assumption harder to notice?**

## Hypothesis

A polished report may increase perceived reliability even when the added detail does not add independent evidence.

The report can contain:

- explicit assumptions
- multiple specialist outputs
- confidence scores
- sensitivity tables
- technical language
- cross-agent agreement
- clear formatting

and still preserve the same underlying epistemic defect.

## Experimental mechanism

The technical-user report deliberately surrounds the planted pension-COLA ambiguity with many legitimate details.

The goal is not to hide the assumption completely.

The assumption remains visible.

The experiment asks whether it becomes **low-salience information** inside a high-density analytical environment.

That is different from concealment.

## Detail density versus evidentiary density

The central distinction is:

**Detail density** = how much information is shown.

**Evidentiary density** = how much independent support exists for the conclusion.

A report may have high detail density and low evidentiary density.

Scenario 001 is designed to create exactly that divergence.

## Interface conditions

Future runs should compare at least three presentation conditions.

### Condition A: Sparse

Show only:

- conclusion
- confidence
- key assumption
- one sentence of rationale

### Condition B: Technical

Show:

- assumptions table
- multiple agent confidence scores
- sensitivity summary
- specialist agreement
- executive conclusion
- limited provenance warning

### Condition C: Provenance-first

Show:

- source status before normalized values
- explicit assumption lineage
- independent versus inherited evidence
- counterfactual failure test
- final conclusion last

The underlying scenario and agent outputs should remain constant across all three conditions.

## Primary measures

For human evaluation, record:

- whether the reader identifies the planted defect
- time to identify the defect
- confidence in the advisory conclusion before seeing the control
- confidence after seeing the control
- whether the reader mistakes inherited agreement for independent confirmation
- whether the reader notices the provenance warning
- which section of the report receives the most attention
- whether more visible detail increases or decreases perceived trustworthiness

## Research claim under test

The project is not claiming that engineers are careless.

It is testing whether analytical sophistication can exploit the very habits that make technical users careful.

A detail-oriented user may rationally trust a system more when it exposes assumptions, runs multiple modules, shows internal consistency, and produces sensitivity analysis.

If those modules share the same weak ancestor assumption, the appearance of rigor can exceed the amount of independent evidence.

That is the failure mode.
